# Plan: Eliminare rol TRODUCER și a tuturor mecanismelor asociate

## Context

Cerință: scoaterea din logica platformei a rolului de user **TRODUCER** și a tuturor mecanismelor, logicii și workflow-urilor legate de troducer.

În cod, **TRODUCER** este un stat intermediar „introducer cu NDA în așteptare”: utilizator cu `referral_code`, fără dashboard complet de introducer (redirect la `/troducer`), creat de admin (Create User / Send NDA pe cerere introducer) sau implicat în validarea codurilor și în fluxul de referral. Eliminarea trebuie făcută fără a rupe fluxurile **PREINTRODUCER**, **INTRODUCER**, invitațiile pe cod și backoffice-ul de onboarding introducer — prin înlocuirea comportamentului cu **PREINTRODUCER** și/sau **INTRODUCER** unde e cazul, și actualizarea contractelor API/UI.

Referință SSOT: `app_truth.md` (secțiuni Referral Code, PREINTRODUCER, duplicate check pe `introducer-nda-request`).

## Hartă a suprafețelor (fișiere și funcții)

### Backend — enum și model

- `backend/app/models/models.py` — `UserRole.TRODUCER` și comentarii asociate.
- `backend/app/schemas/schemas.py` — același `UserRole` pentru API.

### Backend — referral codes (nucleul „type: troducer”)

- `backend/app/services/referral_codes.py` — mapare `UserRole.TRODUCER` → `"troducer"` în `validate_referral_code` / `consume_referral_code`; query-uri `User.role.in_([..., UserRole.TRODUCER, ...])`.

### Backend — contact & auth

- `backend/app/api/v1/contact.py`
  - `POST /validate-code` — returnează `type` din serviciul de mai sus (va dispărea `"troducer"`).
  - `POST /introducer-request` — condiție `code_info["type"] not in ("preintroducer", "troducer")` → doar `preintroducer` (și eventual alte tipuri dacă produsul cere cod INTRODUCER pentru același formular).
  - `POST /introducer-nda-request` — comentariu și logică „cod TRODUCER”; duplicate check pe `(PREINTRODUCER, INTRODUCER, TRODUCER)` → elimină `TRODUCER`.
  - `POST /introducer/upload-nda` — permisiuni `UserRole.TRODUCER` → scoase dacă nu mai există useri TRODUCER.

### Backend — admin

- `backend/app/api/v1/admin.py`
  - `POST /admin/users` (create user): generare referral pentru `PREINTRODUCER` și `TRODUCER`; `nda_signed` pentru `TRODUCER`/`INTRODUCER`; `send_troducer_welcome`; ramuri pentru rol `TRODUCER` la creare cu/ fără parolă.
  - Listare contact requests: `introducer_user_map` filtrează `UserRole.TRODUCER` — înlocuire cu rolurile rămase relevante (ex. doar `PREINTRODUCER`, `INTRODUCER`).
  - `POST /admin/introducer/{request_id}/send-nda` — creează user cu `role=TRODUCER`, `nda_signed=false` → **decizie produs**: înlocuire cu **PREINTRODUCER** (același ciclu NDA + approve ca fluxul public) sau **INTRODUCER** cu `nda_signed=false` (redirect la sign-NDA existent). Recomandat PREINTRODUCER pentru paralelism cu `POST /contact/introducer-request` fără NDA.
  - `PUT /admin/introducer/{user_id}/approve-nda` — filtre `User.role.in_([TRODUCER, PREINTRODUCER, PRE_NDA])` → elimină `TRODUCER`; păstrează upgrade la `INTRODUCER`.

## Algoritmi / fluxuri de înlocuire

1. **Validare cod fără „troducer”**  
   Doar utilizatori cu rol `PREINTRODUCER` sau `INTRODUCER` (și eventual viitorul contract) expun coduri; maparea `UserRole → type` nu mai include `troducer`.

2. **Login → NDA → am un cod → formular introducer**  
   Doar `preintroducer` duce la același formular; codurile `INTRODUCER` rămân pentru buyer (flux existent). Testele 0071 folosesc un cont cu referral plasat pe **INTRODUCER** în loc de TRODUCER.

3. **Admin Send NDA (cerere introducer fără NDA)**  
   User creat ca **PREINTRODUCER** (recomandat): același lanț ca aplicarea publică fără NDA — email NDA, setup password, upload, approve → INTRODUCER. Nu se mai creează niciodată `TRODUCER`.

4. **Admin Create User**  
   Opțiunea TRODUCER dispare; creare directă INTRODUCER rămâne pentru introduceri aprobați administrativ.

5. **Migrare date**  
   Înainte sau împreună cu deploy: toți `users.role = TRODUCER` → PREINTRODUCER (dacă `nda_signed=false`) sau INTRODUCER (dacă produsul decide echivalența), cu verificare manuală pe eșantion.
