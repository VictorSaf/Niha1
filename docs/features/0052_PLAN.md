# 0052 — Fix Document Library download (admin)

## Context

When clicking **Download** on the Document Library page while logged in as **ADMIN**, the document does not download. Example: "Resolution — Carbon Trading Authorization" (`NIHA_Board_Resolution_Carbon_Trading.docx`). Button is the Download control in `DocumentLibraryPage`; DOM path and React component context were provided.

## Root causes (technical)

1. **Backend file path**: The download endpoint serves static files from `DOCUMENT_BASE_PATH` (default `/app/documents`) + `doc["filename"]`. In Docker, the backend only mounts `./backend:/app`; there is no volume or copy that places the catalogued `.docx` files (e.g. from repo root) under `/app/documents`. So the backend returns **404** ("Document file not found on server") for static documents.

2. **Frontend error handling**: `documentLibraryApi.downloadDocument()` uses `responseType: 'blob'`. On 4xx/5xx, axios rejects and the error response body is a Blob. In `DocumentLibraryPage.handleDownload`, the `catch` only does `console.error('Download failed:', err)` — no user-visible feedback. The user sees no download and no message.

## Relevant files and functions

| Area | File | Functions / notes |
|------|------|-------------------|
| Backend download | `backend/app/api/v1/documents.py` | `download_document()` (line ~679): access check, then dynamic PDFs or static `FileResponse(path=file_path, filename=doc["filename"], ...)`. Static path: `os.path.join(os.environ.get("DOCUMENT_BASE_PATH", "/app/documents"), doc["filename"])`. |
| Backend catalog | `backend/app/api/v1/documents.py` | `DOCUMENT_CATALOG` (e.g. id `board_resolution`, filename `NIHA_Board_Resolution_Carbon_Trading.docx`). |
| Docker | `docker-compose.yml` | Backend service: no `DOCUMENT_BASE_PATH`, no volume for document files. |
| Frontend API | `frontend/src/services/api.ts` | `documentLibraryApi.downloadDocument(documentId)`: GET with `responseType: 'blob'`, returns `data` without checking status (success path is 2xx only; on error axios rejects). |
| Frontend page | `frontend/src/pages/DocumentLibraryPage.tsx` | `handleDownload(doc)`: calls `documentLibraryApi.downloadDocument(doc.id)`, creates blob URL, programmatic `<a>.click()`; catch only logs to console. |

## Requirements

1. **Backend**: Ensure static document files are available at the path used by the backend.
   - Use a single source of path: `DOCUMENT_BASE_PATH` env (default `/app/documents`).
   - For Docker: either mount a host directory that contains the catalogued filenames (e.g. a `documents/` folder at repo root or under backend) as `/app/documents`, or document that operators must set `DOCUMENT_BASE_PATH` and provide the files. Do not rely on files that exist only in repo root without being mounted/copied into the container.

2. **Frontend**: When download fails, show a clear error to the user.
   - In `handleDownload`, on catch: set a user-visible error (e.g. state or toast) with a short message (e.g. "Download failed: …"). Prefer the backend error message when available (for blob error responses, the existing API error handler already parses blob-to-JSON for 403; similar parsing can be used in the download flow or a dedicated helper to get `detail` from 404/500 blob body).
   - Ensure the success path is unchanged: create object URL from blob, trigger download, revoke URL, remove temporary anchor.

3. **No mock/cache**: Use real API and real file paths; no mock data or cached blobs.

## Consistency

- Follow existing patterns: `app_truth.md` for config/ports; existing Document Library API and `DocumentLibraryPage` structure; Tailwind tokens and form/button styles per project rules.
- Optional: use `Content-Disposition` filename from response headers for the download attribute if the backend sends it (already set in `FileResponse` and in `_pdf_response`), to avoid relying only on list payload.

## Phases

- **Phase 1 — Backend / infra**: Configure document file location so `download_document` can serve static files (Docker volume or DOCUMENT_BASE_PATH + documented file placement). No change to endpoint logic beyond ensuring the path is correct.
- **Phase 2 — Frontend**: In `DocumentLibraryPage`, surface download errors (state + UI); optionally in `api.ts` or in the page, parse blob error response to show backend `detail` when present.

Phases can be done in parallel if different owners; Phase 2 is independent of where files live, but user will still get 404 until Phase 1 is done.
